# 구현 완료 후 처리

## 시작 전 확인

아래 중 하나라도 해당하면 진행하지 말고 사용자에게 알린다.
- `plan.md` 가 비어 있거나 Status 가 `READY_FOR_IMPLEMENT` 가 아님
- `plan.md` 의 Files 표에 있는 파일 중 구현되지 않은 것이 있음
- Files 표에 없는 파일을 수정했음 (설계 이탈 — 사용자 확인 후 plan.md 에 반영하고 진행)

검증(컴파일, 테스트)을 했다면 결과를, 하지 못했다면 그 사실을 마지막 보고에 그대로 적는다.

## 절차

오늘 날짜는 시스템 날짜로 구한다 (`date +%Y%m%d`, `date +%Y-%m-%d`).

1. **plan.md Status 변경** — `READY_FOR_IMPLEMENT` → `DONE — YYYY-MM-DD`
   - 구현 중 설계와 달라진 점이 있으면 Decision 에 한 줄로 남긴다.

2. **research.md 반영 상태 변경** — 해당 태스크 인덱스의 `반영: 보류` → `반영: 반영됨`
   - 태스크는 plan.md 제목(`## [YYYY-MM-DD] <task>`)으로 찾는다.
   - 다른 태스크의 인덱스는 건드리지 않는다. `폐기` 는 사용자가 직접 기입하는 값이므로 쓰지 않는다.
   - 같은 태스크의 `docs/research/` 문서에 `### Follow-ups` 가 있는지 확인한다. 없으면 구현 중 발견한 범위 밖 정리·리팩토링 후보를 `파일:줄`, 이유와 함께 추가한다 (없으면 "없음").
   - 이번 태스크가 이전 research 문서의 Follow-up 항목을 처리한 것이면, 그 항목 끝에 `→ 처리: docs/research/{이번 파일}` 을 덧붙인다.

3. **exec-plan 보관** — `plan.md` 를 `docs/exec-plan/{YYYYMMDD}-{seq}-{task-name}.md` 로 복사
   - seq: `docs/exec-plan/{YYYYMMDD}-*` 중 가장 큰 순번 + 1, 2자리. 해당 날짜 파일이 없으면 `01`.
   - task-name: kebab-case. 같은 태스크의 `docs/research/` 파일 slug 와 맞춘다.
   - 디렉터리가 없으면 만든다. 같은 이름의 파일이 있으면 덮어쓰지 말고 순번을 올린다.

4. **plan.md 초기화** — 3의 복사본이 생긴 것을 확인한 뒤 아래 내용으로 덮어쓴다.

```markdown
# Plan

<!-- Current plan goes here -->
```

5. **커밋 단위 정하기·메시지 작성** — 아래 "커밋 단위"로 Files 표를 커밋별로 나누고, 커밋마다 "Git 추천 형식"으로 메시지를 쓴다.

6. **로컬 커밋** — 아래 조건을 모두 만족하면 사용자 요청 없이 바로 커밋한다.
   - 3에서 보관한 `docs/exec-plan/` 파일의 Files 표를 기준으로 한다. `plan.md` 는 4에서 초기화되어 Files 표가 남아 있지 않다.
   - 커밋마다 그 커밋에 정한 파일만 경로를 지정해 stage 한다 (`git add -- <파일들>`). `git add -A`, `git add .`, `git commit -a` 금지 — 사용자의 다른 미커밋 변경이 섞이지 않게 한다.
   - 커밋마다 stage 결과(`git diff --cached --stat`)가 그 커밋에 정한 파일과 일치하고, 모든 커밋의 파일을 합치면 Files 표와 일치한다.
   - 자동 검증(컴파일·테스트 등)이 실패하지 않았다. 실패했으면 커밋하지 않고 보고한다.
   - 설계 이탈(Files 표에 없는 파일 수정)이 없다. 있으면 커밋하지 않고 사용자 확인을 받는다.
   - gitignore 여부와 관계없이 Files 표에 없는 파일(research.md·plan.md·docs/ 등)은 커밋하지 않는다.
   - 브랜치: 현재 브랜치에 커밋하고 새 브랜치는 만들지 않는다. 현재 브랜치가 기본 브랜치(main/master 등)인데 그 프로젝트에 기본 브랜치 직접 커밋을 허용한 기록(메모리·프로젝트 CLAUDE.md)이 없으면 커밋 전에 확인한다.
   - 커밋 후 `git log --oneline -<커밋 수>` 와 `git status --short` 로 결과를 확인한다.

7. **PR 설명 초안 (필요한 경우)** — 아래 "PR 설명"의 기준에 해당하면 초안을 써서 마지막 보고에 넣는다. 해당하지 않으면 "PR 설명: 커밋 메시지로 충분"이라고 적는다.

푸시, 브랜치 생성, PR 생성은 사용자가 요청할 때만 한다. 수동 검증 항목은 커밋 후에도 마지막 보고에 남긴다.

## 커밋 단위

Files 표가 성격이 다른 변경을 섞고 있으면 커밋을 나눈다. 따로 리뷰하고 따로 되돌릴 수 있어야 하는 변경은 따로 커밋한다. 아래에 해당하는 것이 없으면 커밋 1개.

- 따로 커밋하는 것
  - 빌드·설정 — `build.gradle`, `pom.xml`, `application*.yml`, CI 설정 등. type 은 `chore`.
  - 이번 기능 밖에서도 쓰는 공용 코드의 동작 변경 — 다른 호출처가 있는 메서드·매퍼·DTO.
  - 프로젝트 규칙이 별도 커밋으로 정한 것 — 예: 공용 라이브러리 버전 올림.
- 같은 커밋에 두는 것
  - 기능 본체와 그 기능의 테스트.
  - 한 변경 때문에 함께 바뀌어야 하는 파일(인터페이스와 구현, 매퍼 XML 과 매퍼 인터페이스).
- 순서는 의존 방향을 따른다 (설정 → 공용 → 기능). 각 커밋이 단독으로 컴파일되는 순서로 정하고, 확신이 없으면 중간 커밋도 컴파일해 확인한다.
- 커밋별 파일·메시지를 정한 뒤 커밋한다. 한 커밋의 메시지에 다른 커밋의 변경을 적지 않는다.

## PR 설명

커밋 메시지는 변경마다 이유를 남기는 기록이다. PR 설명은 리뷰어와 배포 담당자가 머지 전에 알아야 할 것을 적는다. 아래 중 하나라도 해당하면 초안을 쓴다.

- 배포 전에 준비가 필요하다 — DB DDL(사내 데이터구조 변경요청 등), 공통코드·기준 데이터 등록, 환경변수·설정 변경, 다른 저장소와의 배포 순서.
- 이번 기능 밖에도 영향이 있다 — 공용 코드·매퍼 변경, 빌드·CI 동작 변경.
- 커밋이 2개 이상이다.
- research 문서의 API Impact 가 `Breaking: yes` 다.
- 리뷰어가 dev 에서 확인해야 할 수동 검증 항목이 있다.
- 일부러 그렇게 한 설계 판단이 리뷰어에게 버그로 보일 수 있다.

형식 — 해당 내용이 없는 절은 뺀다. 출처는 research 문서(Risks·Follow-ups)와 보관한 exec-plan(Decision·Verification)이다.

```markdown
## 배경
<왜 필요한지 2~3줄>

## 변경 내용
1. <커밋 subject> — <한 줄 요약>

## ⚠ 배포 전 필요
- [ ] <DB·공통코드·설정 등>
- 위 작업 전에 배포되면: <어떻게 되는지>

## 영향 범위
- <이번 기능 밖에서 영향받는 곳>

## 검증
- 자동: <실행해 통과한 것>
- dev 확인 필요
  - [ ] <수동 검증 항목>

## 리뷰 포인트 (의도한 동작)
- <버그처럼 보일 수 있는 설계 판단과 이유>

## 범위 밖 (후속)
- <Follow-ups 중 리뷰어가 알아야 할 것>
```

- PR 은 팀에 공유되므로 비밀번호·키·접속 주소(호스트)·회원 개인정보를 넣지 않는다.
- `🤖 Generated with Claude Code` 같은 AI 생성 푸터를 넣지 않는다.
- 초안만 쓴다. PR 생성·푸시는 사용자가 요청할 때만 한다.

## Git 추천 형식

```
브랜치명: <type>/<short-desc>

커밋 메시지:
<type>(<scope>): <subject>

<body>

<footer>
```

### 브랜치명
- type: `feature` / `fix` / `refactor` / `chore`
- short-desc: kebab-case, 동사-명사 형태 (예: `add-posting-permission`)

### 커밋 메시지
- type: `feat` / `fix` / `refactor` / `chore` / `docs` / `test`
- scope: 주요 변경 레이어 또는 모듈명
- subject: 한글, 50자 이내, 명사형 종결 (예: "게시 권한 검증 추가")
- body: 변경 이유(why) 위주, 문단 단위로 자유롭게 작성. 선택사항.
- footer: 해당 태스크 research 문서의 API Impact 가 `Breaking: yes` 인 경우에만 작성

```
BREAKING CHANGE: <영향받는 API/컨슈머와 변경 내용 요약>
```

### type 선택 기준
| type | 기준 |
|------|------|
| `feat` | 새 기능, 새 엔드포인트 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 코드 개선 |
| `chore` | 빌드, 설정, 의존성 |
| `docs` | 문서, 주석만 변경 |
| `test` | 테스트 코드 추가/수정만 있는 경우 |

### 출력 예시 (일반)
```
브랜치명: feature/add-posting-permission

커밋 메시지:
feat(community): 게시 권한 검증 추가

클럽 컨텍스트에서 WRITE 권한이 있는 사용자만 게시글 작성 가능하도록 제한.
기존에는 클럽 멤버십과 무관하게 인증된 사용자면 누구나 게시 가능했음.
```

### 출력 예시 (Breaking change 포함)
```
브랜치명: fix/change-post-response-schema

커밋 메시지:
fix(community): 게시글 응답 스키마 변경

목록 조회 응답에서 author 필드를 문자열에서 객체로 변경.
프론트엔드에서 작성자 상세 정보를 함께 노출해야 하는 요구사항 반영.

BREAKING CHANGE: GET /api/posts 응답의 author 필드가 string 에서
{ id, name } 객체로 변경됨. krt-fo-web, krt-bo-web 컨슈머 수정 필요.
```

## 마지막 보고

- 보관한 exec-plan 파일 경로
- research.md 에서 `반영됨` 으로 바꾼 태스크
- 검증 결과 (실행한 것 / 실행하지 못한 것)
- 커밋별 해시·메시지와 커밋한 파일, 나눴다면 나눈 기준 (커밋하지 않았다면 그 이유와 커밋 메시지 추천)
- PR 설명 초안 (기준에 해당할 때). 해당하지 않으면 "커밋 메시지로 충분"과 그 이유
- 남은 수동 검증 항목, push 여부
- research 문서의 Follow-ups (범위 밖 정리·리팩토링 후보). 없으면 "없음"
